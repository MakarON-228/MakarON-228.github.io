## 2. Стек и архитектура

### Выбор: Astro + TypeScript + острова

**Почему Astro.** Сайт в основном статический текст, а интерактив — это отдельные виджеты. Astro отдаёт
HTML без JavaScript и подгружает JS только для конкретного виджета и только когда он появляется на экране
(`client:visible`). Это ровно то, что нужно для «много интерактива + оптимизированно»: восемь демок на странице
не тормозят первый экран, потому что до скролла их кода в браузере просто нет.

| Слой | Решение | Почему не альтернатива |
|---|---|---|
| Фреймворк | **Astro** (актуальная версия) | Next.js тащит React-рантайм на каждую страницу; здесь он не нужен |
| Язык | **TypeScript** strict | ловит ошибки в логике демок до браузера |
| Интерактив | **Svelte 5** для UI-островов, **чистый TS + Canvas 2D** для анимаций и игры | рантайм Svelte ~3 КБ; игра и карта на канвасе не нуждаются во фреймворке |
| Стили | обычный CSS с токенами (custom properties), scoped-стили Astro | Tailwind здесь не окупается: айдентика кастомная |
| Аудио | Web Audio API | без библиотек |
| Шрифты | self-host через `@fontsource/*`, woff2, subset latin | Google Fonts добавляет лишний DNS-запрос и блокирует рендер |
| Хостинг | **GitHub Pages** через GitHub Actions (`withastro/action`) | бесплатно, адрес `makaron-228.github.io` |

### Общие правила для каждого острова

- Грузится `client:visible` (терминал — `client:idle`). Исключение — hero-карта: она на первом экране,
  поэтому это разметка из сборки (SVG/HTML) плюс небольшой скрипт на чистом TS, без гидратации; анимацию запускает
  IntersectionObserver.
- До гидратации на месте острова стоит **статичная версия** того же размера: картинка-заглушка или текст с
  результатом по умолчанию. Никакого сдвига вёрстки при загрузке.
- Анимации ставятся на паузу, когда остров вне экрана (IntersectionObserver) и когда вкладка скрыта
  (`visibilitychange`).
- `prefers-reduced-motion: reduce` → никаких автозапусков, только по действию пользователя; переходы мгновенные.
- Canvas: `devicePixelRatio` ограничен 2, перерисовка через `requestAnimationFrame`, без `setInterval`.
- Результаты демок объявляются скринридеру через `aria-live="polite"`.
- `localStorage` только внутри `try/catch`; без него всё работает.

### Движение

Одна срежиссированная сцена: при загрузке по линиям hero-карты трогаются поезда. Всё остальное — микро-реакции
на наведение и клик. Никакого «появления секций при скролле» из `opacity: 0`: контент виден сразу.
Переход по якорям (навигация, станции карты) — плавный (`scroll-behavior: smooth`), при reduced motion — мгновенный.

## 7. Интерактивные элементы — спецификации

Для каждого: что показывает о твоей работе → как взаимодействовать → данные → критерии приёмки.

### 7.1 Hero: карта линий

- **Показывает:** весь путь одним взглядом — линии, станции, время, узел Сириуса.
- **Вид:** SVG (чёткий на любом экране, доступный). Линии в стиле схемы метро: углы 45°/90°, скруглённые изгибы,
  станции — белые круги с обводкой цветом линии, пересадочный узел — капсула.
- **Движение:** по каждой линии бегут 1–2 «поезда» (точки со шлейфом) через `getPointAtLength`. При reduced motion
  поезда стоят на станциях.
- **Взаимодействие:** наведение/фокус на станцию → подсказка (название, дата, результат/роль из §6 — без цифр и
  описаний, чтобы не пересказывать секции); клик → плавный переход к записи. Станции — это `<a>` с `aria-label`,
  работают с Tab. Узел Сириуса стоит в начале 2024 (месяц в §6 не указан).
- **Приёмка:** станции на верных месяцах шкалы; на ширине < 720px карта вертикальная; без JS видна та же карта без
  анимации.

### 7.2 Цифры в записях — перещёлкивание

Отдельного табло «Departures» нет: оно повторяло цифры, которые тут же стоят в записях, и показывало их без
контекста (правило «без дублей», §6.1).

- **Показывает:** выделенные цифры прямо в тексте записей (`**…**` в `resume.ts`) перещёлкиваются, как ячейки
  вокзального табло. Каждая цифра звучит один раз — в своей записи.
- **Какие:** только выделенные фрагменты, в которых есть цифры; меняются только цифры, буквы и разделители стоят.
  Фрагменты без цифр («Sole backend engineer», «every») — обычный жирный текст.
- **Взаимодействие:** наведение мышью или тап → волна слева направо и возврат к значению. При reduced motion — ничего.
  Это микро-реакция (§4), не демка: без фокуса и без `aria-live`, текст — один узел, скринридер и копирование
  видят настоящее значение.
- **Приёмка:** в покое и без JS всегда настоящее значение; строка не дёргается (`tabular-nums`); ни одного нового числа.

### 7.3 LocoLookup — поиск локомотива (TMH, стажировка)

- **Показывает:** реальную логику твоего поискового индекса из `rzd_data_preparation_v2`.
- **Логика (как в репозитории):** запрос нормализуется — пробелы убираются, регистр верхний, латинская `A` в конце
  номера превращается в кириллическую `А`. `61` и `0061` возвращают базовые локомотивы с заводским номером 0061;
  `0061А` возвращает конкретные секции `А`. Один заводской номер встречается у разных серий, поэтому в выдаче
  показаны серия, предприятие и тип результата (locomotive / section).
- **UI:** поле ввода с подсказками-примерами `61`, `0061`, `0061A`, `0061А`; под ним — «query key» после
  нормализации и таблица результатов.
- **Данные:** игрушечный реестр на 30–50 строк с реальными названиями серий (2ТЭ116, 3ЭС5К, ТЭМ18ДМ, ЧС7…) и
  выдуманными номерами и депо. Метка «Illustrative data — the normalisation logic is real».
- **Приёмка:** четыре примера выше дают ожидаемые выдачи; юнит-тесты на нормализацию (vitest).

### 7.4 RailMap — все станции России по дорогам (TMH, стажировка)

Показывает то, что умел твой визуализатор, но на **открытых данных**: все станции сети, фильтр и сортировка по
дорогам. Ничего из данных ТМХ и ничего с твоего компьютера — сайт собирает данные сам.

- **Ориентир:** `reference/tmh-map-original.png` — как выглядела карта в визуализаторе ТМХ (светлая подложка, ходы
  нарисованы цепочками точек-станций, цветные маркеры). Цель — лучше: ходы настоящими линиями, цвет по дороге,
  обе темы, фильтр и поиск. Картинку на сайт не выкладывать.
- **Источник:** OpenStreetMap, `railway=station` на территории России (узлы; полигоны — только если рядом нет
  одноимённого узла) + переключатель «показать платформы» — `railway=halt`. Отсеиваются метро, лёгкое метро, монорельс,
  фуникулёр, детские дороги, `disused`/`abandoned` (среди платформ таких ~1 000) и точки без имени. Лицензия ODbL → на
  карте обязательна подпись «© OpenStreetMap contributors».
- **Сборка данных:** `npm run stations` (`scripts/build-stations.ts`, логика — `scripts/stations/`) тянет данные через
  Overpass API, нормализует (название, координаты, код ЕСР из `esr:user`, если есть), определяет дорогу и пишет
  `public/data/stations.json` (строка на станцию: имя, координаты, группа, ЕСР, тип, оператор) +
  `public/data/railways.json` (сводка по дорогам, покрытие по шагам, точность шага соседей). Результат **коммитится** в
  репозиторий с датой среза OSM — CI не ходит в Overpass при каждой сборке. Перезапуск вручную раз в несколько месяцев.
  Overpass требует User-Agent и бывает перегружен — скрипт перебирает зеркала и не берёт ответ со срезом старше двух
  недель. Сырые ответы кэшируются в `.cache/`; `--cached` перепрогоняет без сети (например, после правок).
- **Определение дороги — главная сложность, проверять обязательно.** Первые цифры кода ЕСР исторически означали
  дорогу, но сейчас есть участки, где станции с одним префиксом относятся к разным дорогам (например, саратовские
  станции Приволжской с префиксом 60) — поэтому префикс только подсказка, не источник истины. Порядок:
  1. теги станции: в OSM `operator` — «ОАО «РЖД»», а дорога лежит в **`operator:branch`**; смотрится он, затем
     `operator`. Если там назван оператор не РЖД — категория «Other railways»;
  2. иначе — связь с Wikidata (`wikidata=Q…`): дорога в свойстве **P127 «владелец»** (P137 «оператор» — РЖД целиком),
     запасные — P137 и P361;
  3. иначе — большинство из трёх ближайших уже определённых станций в радиусе 50 км (по расстоянию); если рядом в
     основном другие операторы или никого — «Unassigned». k и радиус подобраны по leave-one-out: на станциях с дорогой
     из тегов шаг угадывает ≈ 99 %;
  4. ручные исправления — `data/railway-overrides.csv`; они главнее всех шагов.
  Скрипт печатает покрытие по каждому шагу, сверку тегов с Wikidata и список станций, чья дорога расходится с
  доминирующей дорогой их префикса ЕСР, — на ручную проверку. Если эталон не сошёлся или «Unassigned» ≥ 5 %, файлы не
  перезаписываются. Неопределённые станции показываются в категории «Unassigned», а не раскидываются наугад.
- **Other railways:** станции, у которых в OSM явно назван оператор не РЖД — Крымская ЖД, Железные дороги Якутии,
  Газпромтранс, КТЖ, промышленные и ведомственные пути. Отдельная категория, в карточке — оператор из OSM; в долю
  «Unassigned» не входят.
- **16 дорог РЖД:** Октябрьская, Калининградская, Московская, Горьковская, Северная, Северо-Кавказская,

  Восточно-Сибирская, Забайкальская, Дальневосточная.
- **Тесты — станции-эталоны** (управления дорог; в скобках — имя в OSM, если отличается): Санкт-Петербург-Главный →

  Нижний Новгород-Московский → Горьковская, Ярославль-Главный → Северная, Ростов-Главный → Северо-Кавказская,
  Воронеж-1 (Воронеж 1) → Юго-Восточная, Саратов-1 (Саратов I-Пассажирский) → Приволжская, Самара → Куйбышевская,
  Екатеринбург-Пассажирский → Свердловская, Челябинск-Главный → Южно-Уральская, Новосибирск-Главный →
  Западно-Сибирская, Красноярск-Пассажирский (Красноярск) → Красноярская, Иркутск-Пассажирский → Восточно-Сибирская,
  Чита-2 (Чита II) → Забайкальская, Хабаровск-1 (Хабаровск I) → Дальневосточная. Каждый эталон ещё и
  восстанавливается по одним соседям, без своих тегов.
- **Отрисовка:** MapLibre GL JS 6 (WebGL — десятки тысяч точек без тормозов), только слои кругов и заливок: без
  текста на канвасе, шрифтов, спрайтов и внешних запросов. Подложка — **без сторонних тайлов и без границ

### 7.5 AgentPipeline — платформа агентов (Yandex)

Всё в этой демке — **настоящая структура из кода** команды, она уже лежит в `src/data/demo/yandex-agents.ts`:
16 агентов, кто кого читает и сколько символов, какие оценки вытаскиваются, статусы проекта, роли пользователей.
Выдуманы только текст заявки и ответы агентов — это симуляция.

- **Линия статусов проекта** (зелёная линия Agents): `draft → submitted → under_review → accepted_for_research →
  deep_research_running → deep_research_completed → on_showcase`; ответвления `revision_requested` (возврат на
  доработку) и `rejected` (тупик). Решение принимает человек-reviewer — агенты только советуют; это показать явно.
- **Станция «Review» — панель оценки:** четыре эксперта (Technical Analyst, Market Researcher, Innovator, Risk Assessor)
  загораются **одновременно** — в коде они идут параллельно в четыре потока; затем Moderator сводит их в балл 0–100 и
  вердикт APPROVE / REJECT / UNDECIDED.
- **Станция «Deep research» — цепочка из девяти:** Project Analyst → Research Strategist → Technical Researcher →
  Architect → Roadmap Manager → HR Specialist → Risk Analyst → Quality Reviewer → Synthesis Manager. Агенты
  срабатывают **по очереди**, счётчик «3 / 9» как в настоящем UI. Над цепочкой — дуги контекста: кто чьи выводы
  читает, толщина дуги = лимит символов из кода (например, Architect → Roadmap Manager 6000). Risk Analyst выдаёт
  GO / GO WITH CONDITIONS / NO-GO и feasibility score, Quality Reviewer — оценки качества и полноты.
- **Станция «Export»:** два MCP-агента расходятся на Yandex Tracker и SourceCraft.
- **Станция «Showcase»:** карточка проекта на публичной витрине, кнопка «Write to the project» открывает чат.
- **Управление:** выбор одной из 2–3 заготовленных заявок; «Run»; «Skip to result»; клик по любому агенту — его роль и
  что он читает на входе.
- **Метка:** «Simulation — scripted outputs. Agent roster, order, parallelism and context limits are taken from the
  team's code.» Модели в подписи: YandexGPT 5.1 Pro, DeepSeek V3.2 as an alternative profile.
- **Приёмка:** 16 агентов, порядок и параллельность как в коде; при reduced motion сразу финальное состояние.

### 7.6 TwoModels — почему две модели (TMH Hackathon)

- **Показывает:** твоё ключевое решение. Ошибка по децилям показала, что ни одна модель не держит весь диапазон,
  поэтому итоговый прогноз — **взвешенная сумма двух моделей с подобранными коэффициентами**:
  `ŷ = w_A · ŷ_baseline + w_B · ŷ_full`.
- **UI:** график MAE по децилям истинного значения: «Baseline hypotheses», «Full feature set», «Blended».
  Ползунок `w_A` (в демо `w_B = 1 − w_A` — упрощение, подписать); маркер «fitted» на значении, которое находит
  перебор по сетке на валидационной части синтетики. Кнопка «Fit weights» анимирует этот перебор.
  Рядом крупно реальная цифра: **MSE 0.12 on the real data**.
- **Данные:** синтетика с тяжёлым правым хвостом, где базовая модель точнее в середине, полная — на краях.
  Метка «Synthetic data — illustrates the method; the real result is MSE 0.12».
- **Приёмка:** ни одна синтетическая цифра не подписана как реальная; смешанная кривая на подобранном весе ниже
  обеих исходных в среднем; график по правилам — одна шкала, подписи не налезают, цвета из токенов.

### 7.8 RouteFinder — маршруты синтеза (SIBUR)

- **Показывает:** перебор **всех** путей по графу превращений, расчёт требуемых масс, ранжирование по сложности и
  комбинирование источников, когда одного не хватает.
- **Граф — настоящий:** схема превращений модификаций оксида алюминия, с которой работала система. Уже перенесена в
  `src/data/demo/alumina-reactions.ts`: 21 вещество, 24 перехода с температурами, давлением, вакуумом и массовыми
  коэффициентами. Исходник для сверки — `reference/alumina-scheme.png` (на сайт не выкладывать, рисовать свой граф).
- **Контрольные значения для тестов** (посчитаны по файлу данных):
  - к α-Al₂O₃ ведут **29** простых маршрутов из всех вершин графа; из гиббсита — 5, из байерита — 2, из бёмита — 3;
  - по любому маршруту из Al(OH)₃ итоговый коэффициент **1.5301** кг на 1 кг Al₂O₃, из AlO(OH) — **1.1767**:
    масса не зависит от пути (сохраняется алюминий) — отличная проверка, что коэффициенты перемножаются верно;
  - на игрушечном складе максимум корунда: гиббсит 326.8 кг, байерит 78.4, бёмит 68.0, аморфный Al(OH)₃ 39.2,
    диаспор 34.0, нордстрандит 19.6 — всего **566 кг**. 300 кг закрываются одним гиббситом, 450 кг — только
    комбинацией, 600 кг — невыполнимо.
- **Сложность маршрута — иллюстративная модель** (исходная не восстановлена), веса регулируются ползунками прямо в
  демо: `шаг = 1 + w_T · T/1000 + w_P · [гидротермально, 70–90 MPa] + w_V · [вакуум] + 0.5 · [условия не указаны]`,
  маршрут = сумма шагов. Пользователь меняет, что значит «сложно», — и видит, как меняется рекомендация.
- **Комбинирование:** если лучшему маршруту не хватает склада — добирать массу следующими по сложности маршрутами
  из оставшихся запасов (жадно, по возрастанию сложности; каждый источник расходуется один раз на все свои маршруты).
  Это и есть «система линейных уравнений» из CV в упрощённом виде — подписать так.
- **UI:** слева склад (редактируемые остатки) и выбор цели — по умолчанию α-Al₂O₃, можно любую модификацию;
  по центру граф (слоями: гидроксиды → переходные оксиды → α), маршруты подсвечиваются при наведении; справа
  ранжированный список: цепочка с условиями над стрелками, требуемая масса сырья, сложность, хватает ли склада.
  Цепочки с Al(MOₙ)₃ показываются, но без массы («molar mass not defined in the scheme»).
- **Метка:** «Reaction scheme: the real alumina transformation graph the system worked on. Stock levels and the
  difficulty weights are illustrative.»
- **Приёмка:** все контрольные значения выше проходят в тестах vitest; при нехватке склада предложена комбинация или
  честное «not enough stock: max 566 kg».

### 7.9 PitchStaff — YIN на нотном стане (Score Editor) + игра на слух

- **Показывает:** твой собственный алгоритм из `src/audio/PitchDetector.cpp`, работающий в браузере.
- **Алгоритм — порт твоего C++:** разностная функция → кумулятивная нормализация → абсолютный порог **0.1** →
  параболическая интерполяция → `f = sampleRate / τ`; нота: `midi = round(69 + 12·log2(f / 440))`.
- **Источники звука (все три):**
  1. **Микрофон** (на собственном сайте getUserMedia работает) — поёшь или играешь, нота встаёт на стан;
  2. **Экранная клавиатура** — синтез тона с гармониками и лёгким шумом, YIN распознаёт его как «чужой» звук;
  3. **Загрузка аудиофайла** — разбор по кадрам, последовательность нот на стане.
- **UI:** нотный стан (скрипичный ключ, SVG), под ним частота в Hz, название ноты, отклонение в центах.
- **Игра «Ear test»:** звучит случайная нота C4–C6, нужно кликнуть по нужной линейке/промежутку стана; серия
  правильных ответов, лучшая серия в `localStorage`.
- **Растяжка (опционально):** скомпилировать *тот же* C++ `PitchDetector` в WebAssembly через Emscripten и подписать
  «this is the same C++ code as the desktop app». Сильный инженерный ход; делать после всего остального.
- **Приёмка:** синтезированные A4 = 440 Hz и C5 распознаются с ошибкой < 5 центов; при отказе в доступе к микрофону
  понятное сообщение и остальные источники работают; звук стартует только по клику.

### 7.10 RailSnake — мини-игра (Depot)

- **Идея:** «змейка» на сортировочной станции: локомотив собирает вагоны на станциях, состав растёт, скорость
  повышается; упор — буферы и собственный хвост.
- **Управление:** стрелки/WASD, свайпы, экранный крестовина на телефоне; пробел — пауза.
- **Графика:** Canvas, пиксельно-чёткая сетка, цвета линий из палитры; вагоны разных цветов = линии сайта.
- **Счёт:** текущий и лучший (`localStorage`). Общего лидерборда **нет** сознательно: публичная таблица с
  анонимными никами на сайте-резюме — риск, что рекрутер увидит мусор.
- **Приёмка:** 60 fps на среднем телефоне; пауза при уходе со вкладки и при скролле за пределы; старт только по
  действию игрока; игра не перехватывает стрелки, пока не в фокусе.
